# 长期记忆按预算放进上下文，超过阈值后台整理

长期记忆原来每次整份放进会议助手的上下文，靠「最多 100 条、2 万字」的硬上限防止撑爆；到了上限新记忆就写不进去。我们改成两件事：每次运行只按固定字数预算（默认 6000 字）挑最该看的条目放进上下文，其余由会议助手用 `search_memory`、小助理用 `GET /memory?q=` 按需查；记忆超过阈值（默认 1.2 万字或 80 条）时，后台的记忆整理把重复的合并、冗长的精简、过时的删掉。挑选按「和本次会议的相关度（按稀有度加权的字二元组重合）+ 新近 + 常用」打分，「始终记住」的条目和偏好优先。

## Considered Options

- **只靠硬上限**（原做法）：上下文可控，但记忆满了就停止生长，旧的、碎的条目一直占着位置。
- **向量检索**（Mem0、Zep 的做法）：语义匹配更好，但要引入向量库和 embedding 模型，服务器只有 2C2G；我们的记忆量在几百到几千条，字二元组 + 稀有度加权在真实会议上已能把对应的人和项目排在第一。
- **整理用 agent（pi）**：能边查边改，但整理只需要「看一批条目、给出操作」，直接调模型更快、更省；操作由程序逐条校验后再落库。

## Consequences

- 整理的安全规则在程序里而不在提示词里：「始终记住」的不动；用户写过或改过的不删、只能被合并；一批最多直接删除三分之一；都是软删除，写进变更记录（actor=consolidator），可以恢复。
- 自动整理每人每天最多一次；用户可以在记忆页手动「立即整理」。
- `MEMORY_MAX_ENTRIES` 只剩防失控的作用（2000 条）。
